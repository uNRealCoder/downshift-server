Throughput and latency under load

How many requests per second does each server handle, and how long does one request take? Batch 1, JSON bodies, CPU only.

The question

A hand-rolled model server is a short FastAPI file. downshift does more work for each request. It validates the body, runs the model on a thread pool, and keeps the verdict and metrics. This page shows what that costs and what it gives, on four models.

Method

  • Command that made the data: python -m bench.run --out bench/results/v1.0.0/results.json. The file stores its settings. They match --cases clean_mlp tiny_bert mlp_large scatter_include_self_false --skip-workers. The exact command line is not stored.
  • Chart data: python -m bench.report ... --csv bench/results/v1.0.0/chart_runs.csv. Every point on this page is one row of that CSV.
  • Load: closed loop. Each of N clients sends its next request when the last one returns. N is the concurrency (1 to 64). One 1.0 s warm-up and one 3.0 s window for each point.
  • Every server gets the same seeded weights and byte-identical request bodies. Every downshift server is the real downshift serve command. The result cache is off in every row on this page (--result-cache-rows 0).
  • The hand-rolled servers take a plain dict body and return a plain dict. They do less work than downshift for each request. Source: bench/servers.py.
  • async def blocks the event loop. It is a warning row, not a recommended design.

Was the load generator the limit?

Before the sweep, the harness measures the load generator against GET /health on a server that does nothing. This is the ceiling. The highest ratio of any batch-1 result to the ceiling at the same concurrency is 41% (naive torch, async def, clean_mlp, c=1). No result is close to the ceiling.

What this shows and does not show

Shows

  • On the tiny fixtures, a hand-rolled server handles more requests per second than downshift. The HTTP stack is most of the time for one request (see the time page).
  • On tiny_bert, downshift is more than 3 times faster than the hand-rolled eager torch server. The hand-rolled ORT server is faster than downshift.
  • 1.0.0rc1 and 0.5.1 are close. The data shows no gain and no clear loss, except the slow first mlp_large pass.

Does not show

  • One machine. One run. One 3 s window for each point (5 s for MiniLM). The file holds no repeats, so the size of run-to-run noise is not measured.
  • Only 4 models. The 0.5.0 run had 8 models. The 1.0.0rc1 run did not include dynamic_batch_cnn, gnn_gcn, cnn_large or bert_small.
  • CPU only, Windows only. GPU, Linux and other CPUs are not measured.
  • The load generator runs on the same machine as the server. The CPU is shared.
  • No quantised models. No dynamic request batching (downshift has none by design).
