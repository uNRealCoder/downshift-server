The result cache

How much faster is a request that the cache has seen before, and what does the cache cost a request that it has not seen?

Two data sets. A load run of 1.0.0rc1 (2026-11-07T22:59:00) and an in-process check of 0.6.0 (2026-10-14 23:46:17).

Best case: every request is a hit

The question

From 1.0.0, downshift can keep the output of a row and answer a repeated row from memory. It does this only if the row check found the rows of the model independent. This page shows the gain for a repeated request and the cost for a new request.

Method

  • Load run (1.0.0rc1). The variant downshift_cache of bench.run and bench.hf_models uses the default cache. All other 1.0.0rc1 variants add --result-cache-rows 0. The harness sends the same body every time. So after the first request, every request is a hit. This is the best case.
  • Acceptance check (0.6.0). python -m bench.cache_accept --out bench/results/v0.6.0/cache_acceptance.json. It serves all-MiniLM-L6-v2 in the same process with a test client, with the cache on and off. It reads the sum of the stages in the Server-Timing header, so the client time does not count. It is not part of CI.
  • The check has three parts: (a) a query seen before must take under 1 ms; (b) a batch of 32 rows with 30 known rows must run the model on 2 rows; (c) unique queries must cost no more than 5% plus 0.2 ms over a server with the cache off.

With the cache on, the server answers up to about 1900 requests per second (one sentence, c=8). The /health probe, that runs every 50 ms in the same window, sees a higher p99 in the cache-on run than in the cache-off run. The cause is not in the data. The load generator and the server share the machine.

Where the cache does nothing

tiny_bert has dependent rows and scatter_include_self_false has no row check (the numerics check failed). The default cache is off for both. Their cache-on rows are an ordinary run. They differ from the default rows only by run-to-run noise, as the report says. The difference for tiny_bert in the table is a -14.3% change in peak. The size of the noise is not measured, because the file holds no repeats.

A hit takes 18 times less server time than a miss (0.255 against 4.62 ms). A request that always misses takes 4.975 ms with the cache on and 4.8 ms with it off.

What this shows and does not show

Shows

  • A repeated query is answered in about a quarter of a millisecond of server time, against about 4.6 ms for the model.
  • On a batch with known rows, the model runs on the new rows only (2 of 32).
  • A new query costs 0.175 ms more at the median (3.6%) in the one check that was run.

Does not show

  • A normal workload. The load run repeats one body. A real hit rate is not measured.
  • The hardware of the 0.6.0 check. The file stores no machine, CPU or package version. It also stores no spread: only medians, one maximum and the repeat count.
  • The check ran on 0.6.0, not on 1.0.0rc1. It was not run again for 1.0.0.
  • The timing difference between a hit and a miss is visible to a client. The README says that on a server with more than one tenant, a client can see the difference. This is a property of the design, and the data does not measure it.
  • Only MiniLM was checked in-process. The cache for graph models is not measured.
