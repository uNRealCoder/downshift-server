Batches and wire formats

What happens when a request carries 8 or 32 rows, and when the body is safetensors and not JSON?

The question

downshift runs one inference for each request. A client that has many rows can send them in one request. A client can also send binary tensors (safetensors) in place of JSON text. This page shows what each choice does to the rows per second and to the body size.

Method

  • Same command and files as the throughput page. Batch 8 and 32 are in --batch 1 8 32; the batch sweep ran at concurrency 1, 8 and 32. This page uses c=8.
  • rows/s is requests/s times the batch size.
  • downshift_safetensors sends the request as safetensors and asks for a safetensors response. Version 0.5.0 added it. The base64 variant of earlier runs is not in this run.
  • The hand-rolled async server did not run for batches.

What this shows and does not show

Shows

  • For a wide input (mlp_large, 512 floats a row), safetensors gives more than 3 times the rows per second of JSON at batch 32 (25221 against 8022 for 0.5.1), and the body is 5.2 times smaller.
  • For a tiny input (clean_mlp, 16 floats a row) safetensors is slower than JSON in both versions at batch 32.
  • For tiny_bert the safetensors body is larger than the JSON body, because the inputs are short integer lists. The rows per second are still higher with safetensors.

Does not show

  • A real client. The harness encodes the body once and sends the same bytes every time.
  • Batch sizes above 32, or batches of different row counts.
  • Dynamic request batching. downshift has none; one request makes one inference.
  • One machine. One run. One 3 s window for each point (5 s for MiniLM). The file holds no repeats, so the size of run-to-run noise is not measured.
