What the gate catches

Which models pass the gate, and which export hazards does it find? Two sets: 14 small fixtures that each isolate one hazard, and 8 real public models.

Real models: real_models.json, date 2026-11-07. Fixture table: docs/compatibility.md, generated 2026-10-12.

The question

Does the verdict agree with what is true about a model? A hazard fixture has a known right answer. A real model shows whether the gate passes models that people use.

Method

  • Fixtures. python scripts/gen_matrix.py runs downshift.check(..., samples=8) on each model in tests/models/. It writes the table in docs/compatibility.md. This page reads that table.
  • Real models. python scripts/check_real_models.py runs downshift check --json on each model in its own subprocess, on CPU. It writes bench/results/v1.0.0/real_models.json and the second table of docs/compatibility.md. Models: Hugging Face encoders, torchvision ResNet-18 and a PyG GCN.
  • Verification: 8 samples. Some have shapes that the exporter did not see. Tolerance atol 1e-4, rtol 1e-3 (float32). Embedding models also need a minimum cosine of 0.9999.
  • The hub models were read from local copies. downshift never contacts the hub.

What this shows and does not show

Shows

  • The gate passes 8 of 8 models that people use, with errors from 1.2e-07 to 6.0e-05.
  • The gate finds the three kinds of hazard in the fixtures: wrong numbers, no kernel, no export.
  • The check takes 10.6 to 39.0 s for each model on this machine (seconds in the file).

Does not show

  • A false-negative rate. A model that is wrong only on an input that none of the 8 samples hit would pass. The sampled range is small: batch 1 to 4 for the encoders, while the server accepts batch 1 to 4096 (the file marks this as not verified above the sampled range).
  • Any other model family or size. Qwen3-Embedding-0.6B is in scripts/check_real_models.py behind --large. It is not in the file.
  • Speed. These runs check the numbers. They do not load-test the real models (only MiniLM has a load run).
  • The machine. real_models.json stores the date and the package versions. It does not store the operating system or the CPU.
  • Only CPU. The GPU path is not measured.
Source mismatch.The date of real_models.json is 2026-11-07. The second table of docs/compatibility.md says it was generated on 2026-10-12. The file lists torch 2.14.0 and onnxruntime 1.30.0. The doc line lists: torch 2.14.1+cpu, onnx 1.23.2, onnxruntime 1.31.0, torch_geometric 2.8.1, transformers 5.19.0. The numbers in both tables agree. The version text is stale in one of the two files.
