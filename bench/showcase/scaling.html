The question

One downshift process runs inference on one machine. --workers N starts N processes. This page shows what that does to throughput at 1, 8 and 32 concurrent clients.

Method

  • The workers sweep is the last part of python -m bench.run --out bench/results/v1.0.0/results.json. It starts the real CLI with --workers 1, 2 and 4 on clean_mlp, mlp_large and bert_small. Batch 1, JSON.
  • With more than one worker, the parent exports once and hands the artifact to each worker.
  • Data: chart_runs.csv of the 1.0.0 run, with the result cache off in every row, rows with suite = workers.

What this shows and does not show

Shows

  • With 8 or more clients, throughput rises with the number of workers for all three models in both versions.
  • At c=1, more workers do not help. For bert_small 4 workers are slower than 1 (69 against 90 requests/s in 1.0.0).
  • Boot time grows with workers: it is longer with 4 workers than with 1 for every model.

Does not show

  • Linear scaling. The best case is 3.6x for 4 workers. The load generator shares the 16 logical CPUs with the workers, and its ceiling in this run was 8769 requests/s at c=8.
  • Any other model, or a machine with another core count. The two versions are equal on this sweep within noise.
  • Three windows of 1.0.0 had requests that timed out after 30 s or more (--workers 2 c=32 and --workers 4 c=8). Each was measured again and was clean. The cause was the harness: it did not read the output pipe of the server, and a full pipe blocks a log write. The fault is fixed, and a sweep after the fix had no error. The stalled rows are in failed_rows_workers.json, and the repeats in workers_repeats.json.
  • One machine. One run. One 3 s window for each point (5 s for MiniLM). The file holds no repeats, so the size of run-to-run noise is not measured.
