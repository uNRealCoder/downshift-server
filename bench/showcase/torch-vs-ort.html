ONNX Runtime against eager PyTorch

When a model is CLEAN, downshift serves it with ONNX Runtime. How much faster is that than eager PyTorch? First without a server, then through HTTP.

Run 2026-11-07T22:59:00. win32, 16 logical CPUs, Python 3.12.10, torch 2.14.0+cpu, onnxruntime 1.30.0. downshift 1.0.0rc1 from the checkout, 0.5.1 from PyPI. The folder is named v1.0.0, but its data is from the release candidate 1.0.0rc1. Hardware: not recorded in these runs (the files hold the CPU count only).

The question

downshift exists to serve the ONNX graph only when the graph is right. This is worth the work only if ONNX Runtime is faster. This page measures that gain. It does not measure the gate.

Method

  • In-process. python -m bench.inproc <case> <batch> <iters>, started by bench.run with 200 iterations after 20 warm-up calls. It calls the backend on arrays that are already in memory. No HTTP. Three levels: compute only; compute + JSON (parse the body, infer, write the response); compute + base64. Source: bench/inproc.py. Data: results.json, key inproc.
  • Over HTTP, MiniLM. python -m bench.hf_models --out bench/results/v1.0.0/results_hf.json (5 s windows, c=1 and c=8). --backend torch forces eager PyTorch in the same downshift server. All other settings are equal.
  • Over HTTP, fixtures. The two hand-rolled servers (FastAPI + torch, FastAPI + ORT) use the same weights and graph. See the throughput page.

The gain of ONNX Runtime falls with the input size: 3.3x for one sentence, 1.9x for eight sentences, 1.3x for about 180 tokens. The hand-rolled server runs eager torch. downshift with --backend torch is close to it (146 against 141 requests/s). The hand-rolled server cuts over-long text. downshift rejects it.

What this shows and does not show

Shows

  • Without a server, ORT is 1.4x to 7.4x faster than eager torch on the CLEAN models and batch sizes measured.
  • On a real encoder behind HTTP (MiniLM), ORT gives 1.3x to 3.3x more requests per second than eager torch in the same server, and the gain is largest for short inputs.
  • The gain does not carry over to every model over HTTP (see mlp_large).

Does not show

  • Any GPU result. Torch threads were 8 and the ORT provider was CPU (the file lists Azure and CPU providers).
  • Why a result differs. The files hold no profile.
  • ORT with graph optimisation or quantisation. downshift does neither.
  • One machine. One run. One 3 s window for each point (5 s for MiniLM). The file holds no repeats, so the size of run-to-run noise is not measured.
  • The in-process numbers use 200 calls. The p50 is stable, but the tail (p99) of 200 calls is not.
